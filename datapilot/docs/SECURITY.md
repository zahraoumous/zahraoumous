# Local edition security and operational limits

This is a real local workflow, not a certified production service. Keep loopback bindings for local use. Before exposing it to a network, configure TLS, exact `DATAPILOT_APP_ORIGIN` and secure cookies (`DATAPILOT_COOKIE_SECURE=true`), replace example infrastructure passwords and review backups/retention. OIDC, email verification, password reset, invitations, organization administration and production abuse controls are separate work.

Sessions are random opaque tokens stored only as SHA-256 hashes in PostgreSQL, with seven-day expiry. Passwords use scrypt n32768/r8/p3 and random salts. No default application account is seeded. Mutating requests require an allowed Origin, including sign-in/sign-up to prevent login CSRF. Auth throttling uses Redis and fails closed if unavailable. All workspace-scoped reads/writes check active organization membership; viewers cannot import, retry, apply cleaning, create analyses or change dashboards.

Uploaded paths are normalized display metadata and must be relative, unique within a batch, and free of traversal or control characters. Object keys are generated from workspace/version UUIDs. Body, file, count and aggregate limits are enforced server-side; original objects are not rewritten. Failed persistence rolls back metadata and attempts to remove uploaded unreferenced objects. Periodic cleanup of orphaned objects and expired session rows is future maintenance work.

The parser never evaluates client-supplied Python, SQL or spreadsheet formulas. It runs after credentials are removed from its environment and OS restrictions are applied. In the standard Docker topology the orchestrator uses limited root capabilities to make per-job chroots and switch the parser to a fresh non-root identity. It has no host mounts, Docker socket, SYS_ADMIN or privileged mode. The parser has no credentials, no network access and no sibling job filesystem access. Resource limits and strict bounded output validation complement that boundary. A memory-corruption vulnerability in an underlying library is still a reason to keep dependencies updated and use stronger microVM/container isolation for a production pilot.

Only one beat scheduler should dispatch this local stack. This release is not a design for scaling arbitrarily many root-capable orchestrators. Backup both PostgreSQL and object storage. No automated retention, quotas across all historical imports, backup/restore runbook or production container scan is claimed by this release.

Quality checks and inferred types are descriptive. They do not establish business semantics, correct accounting, complete validation or an absence of sensitive data. Previews remain within the authenticated workspace. Cleaning applies only a previously previewed, explicitly approved plan and creates an immutable child version; original objects are preserved. Business metrics use the user-confirmed column roles and saved filters, with exclusions recorded as evidence. CSV/XLSX exports escape formula-like text; review exported content before sharing it.

## AI settings and external providers

AI settings belong to the signed-in local account. API keys are accepted only over the authenticated, origin-checked settings endpoint. Responses contain a saved-key flag and masked last-four-character hint, never the full key. Keys are encrypted at rest with authenticated Fernet encryption. The encryption key derives from `DATAPILOT_AI_KEY_ENCRYPTION_SECRET` when nonempty, otherwise from the existing object-storage secret (`MINIO_ROOT_PASSWORD` in Compose) with a separate application context. Set a long random separate secret before first saving provider keys, keep it stable across updates, and back it up securely. Changing or losing the active encryption secret requires users to re-enter saved API keys; automatic key rotation is not implemented. A blank key retains the current provider's key, explicit clear removes it, and switching provider removes the previous key unless a replacement is supplied.

Local mode needs no key and sends no data externally. It presents deterministic evidence according to one of three fixed skills and explicitly states that it does not interpret arbitrary questions or infer causes. For OpenAI, Anthropic or Gemini, each question requires explicit consent to send that question and aggregate evidence. The payload contains dataset/column names, quality counts and saved analysis aggregates, mapping and filters; it omits raw source rows. Names, filters and the question itself can still contain sensitive information, so review the disclosure before opting in. Provider retention and processing terms also apply.

External requests use only the fixed HTTPS hosts `api.openai.com`, `api.anthropic.com` and `generativelanguage.googleapis.com`. Arbitrary base URLs are unsupported; redirects are refused so credentials cannot be forwarded elsewhere. Requests have a 25-second socket timeout, a 256-KiB response limit and a requested 1,200-token output limit. Provider errors are sanitized. Model outputs and uploaded text are never executed as code, SQL, tools or automatic cleaning actions. Fixed system instructions treat the question, names and evidence as untrusted input, but generated commentary can still be wrong; numerical claims must be checked against the attached evidence. Questions and answers are stored in workspace-scoped conversations and provider/model/skill selections are recorded in audit metadata. No API keys enter prompts or audit records.

Provider credentials, model access, outbound network policy and quota must be available in the deployment for external AI. This release verifies provider adapters with mocked HTTP responses; it does not claim a successful live request without credentials. Production AI rate limits, spending caps, retention controls and key rotation remain deployment work.
